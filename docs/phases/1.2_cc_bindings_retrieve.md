# Phase 1.2 — CC: bindings retrieve fields (unblock FAQ)

**Wave:** CC safety  
**Depends:** 0.1 (1.1 recommended first, not required)  
**Unlocks:** safe Inform/FAQ editing; 2.4 create-from-UI  
**Lock:** [PROGRAMME.md](./PROGRAMME.md)

---

## Operator outcome

I can add or edit a “Media Gateway” FAQ and the bot still finds it when the caller mangles the name. Saving does not wipe intent / department / product / aliases.

---

## Goal

Make the Bindings form match VA.5 / NC.6 retrieve keys. Stop reconstructing `{ id, questions, text }` only.

---

## In scope

Per **inline_faq** entry, show and persist:

| Field | Operator meaning |
|---|---|
| `id` | Stable entry id |
| `text` | Answer per locale (already there) |
| `questions` | Phrases a caller might say (already there) |
| `aliases` | Noisy / roman STT variants (“media gate bhege”) |
| `intents` | Catalog intent ids this entry answers (`product_question`, `media_gateway`, …) |
| `department` | Room steer (`sales` / `support` / `billing` …) — not a hard block |
| `product` | Product steer (`IRIS IVDX`, `Media Gateway`, …) |

- Load: keep the full entry object (`...e` on patch).
- Save: send `entries` as the loaded/edited array — **never** rebuild a slim object.
- New entry template includes empty arrays/strings for the new fields so later edits have a place to write.
- **Remove Delete binding.** Keep Disable / Enable. Copy already says the API has no DELETE; the button must go (client `deleteBinding` may stay unused or be deleted).
- List hint: “These fields are how the bot finds the answer — not just the words.”
- Intent chips: if a CC profile catalog is available (optional fetch of latest profile), suggest ids; otherwise free chips with the same id pattern as intents (`^[a-z0-9][a-z0-9_]{0,63}$`).

## Out of scope

- http_retrieve extra fields beyond today’s `gateway_id` + `path`.
- CRM binding shape (leave as today).
- Changing Inform runtime.

---

## Backend contract (read-only)

`internal/runtime/graph/inform.go` `inlineFAQEntry`:

- `questions`, `aliases`, `intents`, `department`, `product`, `text`
- Retrieve key is intent + department + product + query; aliases score noisy STT
- No `DELETE /v1/bindings/{id}` in `internal/control/server.go` — only `GET`/`PUT`
- Inactive `status` stops Inform (`inform.go` refuses non-active)

Live lab entries on `product-faq` and `coral-telecom-limited-faq` already have intents / department / product / aliases.

## Current baseline

- `src/pages/Bindings.jsx` — editor for `id`, `questions`, `text` only; `setEntry` spreads (good); **new** entries are `{ questions: [] }` only.
- `removeBinding` calls `api.deleteBinding` → will 404.
- `src/api/types.js` — `InlineFaqEntry` missing aliases/intents/department/product.
- `src/api/client.js` — `deleteBinding` exists; backend does not.

## UX

- Each entry is a card: identity row (id, department, product), then intents + aliases + questions, then locale text.
- Helper under intents: “Must match an intent id on the profile that will use this binding.”
- Disable is the only “remove from calls” action; confirm copy stays.

## Exit criteria

1. Saving `product-faq` without touching extra fields leaves `intents`, `department`, `product`, `aliases` intact.
2. A new entry can set all four retrieve fields and they survive reload.
3. Delete binding control is gone; Disable / Enable still works.
4. Types/docs match the Go entry shape.

---

## Verify

- GET `/v1/bindings/product-faq` → note one entry’s `intents`.
- Open Bindings, click that binding, Save without edits → GET again → same intents/product/department/aliases.
- Add a dummy entry with aliases + intent → Save → GET → present → delete the dummy by editing the array (or disable whole binding only if you created a throwaway binding).

## Risks

| Risk | Mitigation |
|---|---|
| Form rebuilds entries from displayed fields only and drops unknown keys | Always spread the original entry |
| Operator puts a dial number in `product` | Not a binding publish rule; do not invent validation beyond non-empty id |
