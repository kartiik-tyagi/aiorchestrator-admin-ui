# Phase 2.3 — CC: dashboard / pins / setup strip

**Wave:** CC sync  
**Depends:** 0.1 (paths), 2.1–2.2 recommended so copy can mention intents/globals  
**Unlocks:** 2.4  
**Lock:** [PROGRAMME.md](./PROGRAMME.md)

---

## Operator outcome

I know why a DID will not answer, in plain language, and I can prove a pin with one click.

---

## Goal

Dashboard and pins tell the **operator** truth, not only `platform/status`. One-pin edits must not rewrite the whole pin list by accident.

---

## In scope

### Dashboard (`/CC/admin`)

- Keep existing stats (ready, db, profile/flow/binding/pin counts).
- Keep `readinessChecklist` (stricter than server `ready_for_sessions`).
- Map blockers to screens (`tenant_engines_missing` → Engines, etc.).
- **Warnings** (not fake blockers) when:
  - a live pin’s profile has an empty `intent_catalog` (agent turn will be edge-only);
  - a published flow has Inform nodes but no binding / empty retrieve keys;
  - a published flow has `kind=global` edges but empty `globals`.
- Setup strip stays the six steps; all `to` values under `/CC/admin`.
- Copy: “Server Ready can still refuse calls without a pin.”

### Pins (`/CC/admin/pins`)

- Keep bulk save (`PUT /v1/tenant/answer-pins`).
- Add **per-row save** via `PUT /v1/tenant/answer-pins/{profile_id}` when editing one pin (less chance of wiping others).
- Delete one pin via `DELETE /v1/tenant/answer-pins/{profile_id}` with confirm.
- Smoke test unchanged: `POST /v1/sessions` `clock=chat` → `answer` → show spoken → `stop`.
- Show pin `did` and `note` fields (already in the type).

### Client

- `getAnswerPin`, `putAnswerPin`, `deleteAnswerPin`.
- Optional: `GET /v1/tenant/config` as a single prefetch for dashboard/engines later (use if it reduces calls; not required).

## Out of scope

- New pin data model.
- Supervisor session list.
- Rewriting Tutorial (2.4).

---

## Backend contract (read-only)

- `GET/PUT /v1/tenant/answer-pins`
- `GET/PUT/DELETE /v1/tenant/answer-pins/{profile_id}`
- `GET /v1/platform/status` — `ready_for_sessions` does **not** require a pin (this is why the UI checklist exists)
- Session create/answer/stop already used by Pins.jsx

---

## Current baseline

- Dashboard + `SETUP_STEPS` + `readinessChecklist` already good; paths must stay `/CC/admin/…` after 0.1.
- Pins: bulk PUT only; smoke test exists; `stopSession` on cleanup.

## UX

- Blockers: red row + one button (“Bind engines”).
- Warnings: amber, not blocking publish.
- Pin row: Save this pin | Test | Remove.
- Smoke test result: spoken line or “Bot said nothing — check Entry → Speak.”

## Do / Do-not

- **Do** keep chat smoke-test; always stop the session.
- **Do not** treat server `ready_for_sessions` as “calls will work”.
- **Do not** replace all pins when the operator meant to change one note.

---

## Exit criteria

1. A missing pin and a missing engine each send me to the right page in one click.
2. Editing one pin’s note does not require rewriting all pins unless I use “Save all”.
3. Smoke test still works on the three live pins.
4. Dashboard warnings appear for empty catalog / empty `globals` only when those GETs say so — no false warnings on the live inbound flow (it has both).

---

## Verify

- Unpin mentally: look at checklist with pins loaded (live lab has 3 — all green).
- Change one pin note via per-row save → GET list → only that note changed.
- Run smoke test on `coral-telecom-limited` pin → greeting text → session stopped (`GET /v1/sessions/{id}` not required).
