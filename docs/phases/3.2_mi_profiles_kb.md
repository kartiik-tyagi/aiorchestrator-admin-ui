# Phase 3.2 — MI: profiles + KB

**Wave:** MI  
**Depends:** 3.1  
**Unlocks:** 3.3 (meetings need a profile_id)  
**Lock:** [PROGRAMME.md](./PROGRAMME.md)

---

## Operator outcome

I can create the meeting “desk” — languages, MoM sections, rules, memory, retention — and paste a policy KB doc. I understand that changing a profile does **not** rewrite past meetings.

---

## Goal

CRUD UI for MI profiles and KB that round-trips the **store fields**, not CC `Document`.

---

## In scope

### Routes

- `/MI/admin/profiles` — list + create
- `/MI/admin/profiles/:id` — edit + KB

### Profile fields (from store / facade tests)

| Field | UI |
|---|---|
| `name` | Text |
| `languages` | Locale chips (may be JSON array; accept array or parse string) |
| `mom_template.sections[]` | Ordered id + title |
| `rules` | Known key `rules.case_b.min_segments` as a number field; **Advanced JSON** for the rest of `rules` so we do not invent schema |
| `memory_policy` | Structured if we see a stable shape on GET; else JSON editor |
| `b_authority_policy` | Same |
| `retention.transcript_days` | Number |

Create: `POST /mi/v1/profiles`.  
Update: `PUT /mi/v1/profiles/{id}` — send full object loaded + patched.  
**No delete.**

### KB

- List: `GET /mi/v1/profiles/{id}/kb`
- Upsert: `PUT /mi/v1/profiles/{id}/kb/{doc_id}` with `title` + `body` (match live body; if the server asks for more fields, show them after first GET)

### Copy

“Updates apply to **new** meetings. Meetings already created keep the snapshot they were born with.”

## Out of scope

- Profile Ask box (3.5).
- Action ledger (3.5, if routes exist).
- Meetings list on the profile page beyond a link “Meetings for this profile” to 3.3 with `?profile_id=`.

---

## Backend contract (read-only)

- `POST/GET /mi/v1/profiles`, `GET/PUT /mi/v1/profiles/{id}`
- `GET …/kb`, `PUT …/kb/{doc_id}`
- V1: **no profile delete** (`web/mi/index.html` and doc 08)
- PUT does not rewrite past meeting pins (doc 08 §3)

Live create example from tests: `name`, `languages`, `mom_template`, `rules`, optional `memory_policy`, `retention`.

---

## Current baseline

- No MI profile pages.
- Client methods from 3.1.

---

## UX

- List: name, id, language chips, updated time.
- Editor: sections as an ordered list (add/remove/reorder).
- KB: list of docs; click to edit; new doc asks for `doc_id` once (immutable id).
- Advanced JSON for leftover `rules` sits **below** the known fields; saving merges JSON into `rules` without dropping `case_b.min_segments` unless the operator edited that JSON.

## Exit criteria

1. Create + reload + edit name round-trip matches GET.
2. KB doc appears in list after upsert and reloads.
3. Screen copy states snapshots are not rewritten.
4. Empty `mom_template.sections` is allowed if the server allows it; invalid JSON in Advanced rules does not save.
